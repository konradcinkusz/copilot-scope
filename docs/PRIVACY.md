# Privacy, works councils and GDPR

CopilotScope measures how AI coding assistants perform. That means it processes data
generated by identifiable people at work, which in the EU makes it a *technical system
capable of monitoring employee performance* — and the capability, not the intention, is
what triggers co-determination under German BetrVG §87(1)(6) and the equivalent regimes
elsewhere. "We don't use it that way" is not an answer a works council can accept, because
it cannot be verified and it cannot be enforced.

This document is the answer instead. It describes what the software collects, what
**privacy mode** enforces in code, how long data lives, and it includes a template annex a
works council can attach to a Betriebsvereinbarung.

> **Scope of this document.** CopilotScope is self-hosted: you run the collector, you own
> the database, and no data reaches the project's maintainers. Everything below describes
> the software's behaviour. The controller under GDPR Art. 4(7) is your organization, and
> the Art. 30 record is yours to keep — §2 gives you the technical half of it.

## 1. Privacy mode

Off by default, because a developer watching their own sessions on a laptop has no data
subject to protect but themselves. On, it enforces four things:

```jsonc
// appsettings.json / environment
{
  "CopilotScope": {
    "Privacy": {
      "Enabled": true,
      "Salt": "<a long random secret, kept stable and stored separately>",
      "MinimumGroupSize": 5,
      "SuppressSessionDetail": true,
      "AuditLog": true,
      "PseudonymizeBranch": false,
      "AllowRawForwarding": false
    }
  }
}
```

Environment-variable form: `CopilotScope__Privacy__Enabled=true`, and so on.

| Control | What it does | Where |
|---|---|---|
| **Pseudonymization at ingest** | Every identifying attribute is replaced by a salted HMAC-SHA256 token *before* anything aggregates it. Nothing downstream — the session store, the Postgres snapshot, the Prometheus exporter — ever holds the original value, so the guarantee survives a database dump. | `Privacy/PrivacyRedactor.cs` |
| **No content retention** | Prompt and response text is dropped, not tokenized. Client-side `captureContent` can be left on by mistake; privacy mode makes that harmless. | `Privacy/PrivacyRedactor.cs` |
| **Aggregation floor (k-anonymity)** | No view renders unless it covers at least `MinimumGroupSize` **distinct subjects**. Fifty sessions from one developer are one subject, and stay withheld. Per-session detail is refused outright, because a single session is a group of one. | `Privacy/KAnonymity.cs` |
| **Access audit log** | Every read of session data records who, what, when and whether it was served or withheld — deletions included. Exportable as CSV. | `Privacy/AccessAudit.cs` |
| **Per-session Prometheus series off** | `Prometheus:PerSession` exports one series per session, labelled by session id and carrying that session's score. Privacy mode refuses it: `/metrics` is not a less sensitive surface for being a different port. Team aggregates still export. | `Api/PrometheusExporter.cs` |

Verify a running deployment with `GET /api/privacy` — it reports what is enforced, plus
live counters for attributes pseudonymized and content dropped. The dashboard shows a
persistent banner whenever privacy mode is on, so the people being measured can see the
controls without reading the configuration.

### The salt is load-bearing

The identifier space here is tiny and guessable — the hostnames and work email addresses of
one company. An **unsalted** hash of those is invertible with a wordlist in seconds, which
is not pseudonymization in the sense GDPR Art. 4(5) means; re-identification must require
"additional information kept separately". So:

- Set `CopilotScope:Privacy:Salt` to a long random secret.
- Store it where the telemetry database is **not** — a secret manager, not the same
  connection string. Salt plus database is re-identification; either alone is not.
- Keep it stable. Changing it re-pseudonymizes everyone, and history stops correlating
  across the change.

If it is left empty the collector generates one per process and logs a warning at startup.
That is usable for a trial and useless for a deployment.

### What privacy mode deliberately does *not* do

- It does not encrypt the database. Use your platform's encryption at rest.
- It does not stop someone with Postgres access from reading rows directly. It limits what
  those rows contain, which is the durable control.
- It does not pseudonymize the **repository** name (needed to group work) and, by default,
  not the **branch** either — branch names are how sessions link to pull-request outcomes.
  Where branch naming embeds people (`konrad/fix-login`), set `PseudonymizeBranch: true`
  and accept that outcome linkage stops working. This is the operator's trade-off, and it
  belongs in the works agreement.
- It blocks **raw OTLP forwarding**, which relays payloads upstream exactly as they
  arrived — before redaction, by design. Set `AllowRawForwarding: true` only if the
  upstream backend is covered by the same agreement.

### Related: workflow-friction signals

The one analyzer that reads prompt text is documented separately in
[`WORKFLOW_FRICTION.md`](WORKFLOW_FRICTION.md) — what it measures (observed repair events,
not emotion), why EU AI Act Art. 5(1)(f) makes that distinction load-bearing, and why it
ships switched off. Privacy mode makes it moot: with content dropped at ingest the analyzer
has nothing to read and reports no data.

## 2. Data map (GDPR Art. 30)

What the collector receives, per emitter. Everything here is what the assistant chooses to
send; CopilotScope has no agent on the developer's machine and cannot collect anything the
emitter does not export.

### 2.1 Always collected (all emitters)

| Category | Attributes | Personal data? | Under privacy mode |
|---|---|---|---|
| Session identity | `session.id`, `gen_ai.conversation.id`, `claude_code.session_id` | Indirectly — a session belongs to one person | Kept (already opaque, client-generated) |
| Machine identity | `host.name`, `host.id`, `service.instance.id`, `process.pid`, `container.id`, `k8s.pod.name` | **Yes** — a hostname is usually a person | **Pseudonymized** |
| User identity | `enduser.id`, `user.name`, `user.email`, `os.user`, `claude_code.user.account_uuid`, `github.copilot.user` | **Yes** | **Pseudonymized** |
| Organization | `organization.id`, `claude_code.organization.id` | No | Pseudonymized |
| Work context | `github.copilot.git.repository`, `github.copilot.git.branch` | Repository: no. Branch: **possibly** | Repository kept; branch kept unless `PseudonymizeBranch` |
| Model usage | `gen_ai.request.model`, `gen_ai.response.model`, input/output/cache token counts | No | Kept |
| Timing | span start/end, `time_to_first_token`, tool-call durations | No | Kept |
| Outcomes | tool names, `error.type`, edit accept/reject counts, thumbs up/down, lines added/removed | No — counts, not content | Kept |
| Connection | remote IP of the ingest connection (used only to tell machines apart; never stored) | **Yes**, transiently | Used for scoping, not persisted |

### 2.2 Content — only when the client opts in

| Attribute | Emitted when | Under privacy mode |
|---|---|---|
| `gen_ai.input.messages`, `gen_ai.prompt` | VS Code `captureContent`, SDK content capture | **Dropped at ingest** |
| `gen_ai.output.messages`, `gen_ai.completion` | as above | **Dropped at ingest** |
| Claude Code `prompt` on `user_prompt` | `OTEL_LOG_USER_PROMPTS=1` | **Dropped at ingest** |
| Claude Code `response` on `assistant_response` | `OTEL_LOG_ASSISTANT_RESPONSES=1` | **Dropped at ingest** |
| GenAI content-event log bodies | emitter-dependent | **Dropped at ingest** |

Without privacy mode these are stored in the session snapshot and shown in the dashboard's
"Prompts & responses" panel to admin-role users only. **This is source code and whatever
was pasted alongside it.** If content capture is on anywhere in your fleet, that fact
belongs in the works agreement explicitly — or turn privacy mode on and make it moot.

### 2.3 Per-emitter differences

Which signals each assistant actually sends is documented in
[`SIGNAL_COVERAGE.md`](SIGNAL_COVERAGE.md) and served live from `GET /api/coverage`.
Emitters that send less are not more private by design — they simply report less.

### 2.4 What is never collected

- File contents, diffs, or the code an edit applied.
- Keystrokes, screen contents, active-window titles, idle time.
- Anything from a machine that is not running an assistant configured to export to your
  collector.
- Embedded credentials in repository URLs — stripped before display or storage.

## 3. Retention and deletion

| Data | Default retention | Configure | Delete |
|---|---|---|---|
| Session snapshots (Postgres) | Indefinite | `CopilotScope:History:RetentionDays` — a background sweep every `SweepInterval` (6h) deletes past the window, in the database and in memory | `DELETE /api/sessions/{id}` (Admin scope) |
| Session aggregates (memory) | Most recent 200 sessions | fixed | evicted automatically; the Postgres snapshot survives |
| Access audit log | Independent of session retention, and deliberately longer | `access_audit` table | manual — it must outlive the sessions it describes, or it cannot answer "who read the data you deleted" |
| Pull-request outcomes | Indefinite, opt-in feature | `CopilotScope:Outcomes` | drop the `pull_request_outcomes` table |

Set a retention window. `RetentionDays: 90` is a defensible default for a tool whose
purpose is trend analysis: it is long enough to see a quarter, short enough that GDPR
Art. 5(1)(e) storage limitation is satisfied by the software rather than by a promise.

**Data subject requests.** Under pseudonymization the collector cannot map a token back to
a person — that is the point, and Art. 11 recognizes it. To service an access or erasure
request you need the salt and the person's host/user identifier; compute the token, then
find and delete the matching sessions. Document this procedure alongside wherever you store
the salt.

## 4. Access control

Privacy mode is not a substitute for authentication. Configure both:

- **Scoped collector keys** (`CopilotScope:Keys`) — `Ingest` for the editors, `Read` for
  the dashboard, `Admin` for deletion and the audit export. The key handed to every
  developer's editor must not be the one that can wipe history.
- **Dashboard sign-in** (`CopilotScope:Dashboard:Auth`) — a viewer password and an admin
  password. Transcripts and deletion are admin-only.

The dashboard forwards the signed-in role to the collector on every call
(`X-CopilotScope-Actor`), so the audit log names a person rather than "the dashboard".

Read the audit log with `GET /api/audit?format=csv` (Admin scope).

## 5. EU AI Act

Provisions covering high-risk employment and worker-management systems (Annex III) apply
from 2026-08-02. Whether a given CopilotScope deployment falls in scope depends on how you
use it, not on the software: a tool used to evaluate *the assistants* is not an
employment-decision system, and a tool used to rank *developers* is. CopilotScope's
documented non-goals (README, "Not for performance reviews") and privacy mode's
aggregation floor are what keep a deployment on the first side of that line — the floor in
particular makes the per-developer scoreboard technically unavailable rather than merely
discouraged.

This is not legal advice. Have your DPO assess your deployment.

## 6. Template: works-agreement annex

A starting point for a Betriebsvereinbarung annex or an equivalent works-council
agreement. It is a template, not a legal document — have counsel review it, and check every
statement against your actual configuration (`GET /api/privacy` reports it).

> ### Annex: CopilotScope (AI assistant telemetry)
>
> **1. Purpose.** CopilotScope is operated solely to assess the quality, cost and latency of
> AI coding assistants used in the organization, and to inform decisions about which
> assistants and models to provide. It is not operated to assess the performance, conduct
> or productivity of individual employees.
>
> **2. Data processed.** Only the categories listed in §2 of the CopilotScope privacy
> documentation, in the version attached to this annex. No prompt or response content, no
> file contents, no keystrokes, no screen contents and no idle-time measurement.
>
> **3. Pseudonymization.** Identifying attributes (machine names, user identifiers) are
> replaced by non-reversible tokens before storage. The secret enabling re-identification
> is held by [ROLE] and stored separately from the telemetry database. Re-identification
> may take place only [DESCRIBE THE CASES — e.g. never; or only at the request of the
> employee concerned].
>
> **4. Aggregation floor.** No evaluation may be displayed for a group smaller than
> [k = 5] employees. The system enforces this technically; views below the floor do not
> render. Per-session views are disabled.
>
> **5. No individual evaluation.** Data from CopilotScope shall not be used in performance
> appraisals, target agreements, disciplinary proceedings, or decisions on hiring,
> promotion or termination. It shall not be combined with other systems for the purpose of
> individual assessment.
>
> **6. Access.** Access to the CopilotScope dashboard and API is limited to [ROLES]. Every
> read is logged with actor, time and scope. The works council may request the access log
> at any time and receives it within [N] working days.
>
> **7. Retention.** Session data is deleted automatically after [N] days. The access log is
> retained for [N] months.
>
> **8. Changes.** Any change to the configuration items in §1 of the CopilotScope privacy
> documentation — in particular privacy mode, the aggregation floor, content capture, or
> upstream forwarding — requires the prior consent of the works council. The current
> configuration is available at all times at `GET /api/privacy`.
>
> **9. Termination.** On termination of this agreement, all data collected under it is
> deleted within [N] days.

## 7. Checklist for a compliant deployment

- [ ] `CopilotScope:Privacy:Enabled = true`
- [ ] `CopilotScope:Privacy:Salt` set to a long random secret, stored separately from the database
- [ ] `MinimumGroupSize` agreed with the works council (5 or higher)
- [ ] `CopilotScope:History:RetentionDays` set
- [ ] Scoped API keys configured — ingest keys cannot read
- [ ] Dashboard sign-in enabled
- [ ] `AllowRawForwarding` left off, or the upstream backend covered by the same agreement
- [ ] Content capture off on every client (belt and braces — privacy mode drops it anyway)
- [ ] `/metrics` reachable only by the monitoring stack (privacy mode already drops the per-session series)
- [ ] `CopilotScope:WorkflowFriction:Enabled` left off, or covered by the works agreement (see [WORKFLOW_FRICTION.md](WORKFLOW_FRICTION.md))
- [ ] `GET /api/privacy` output attached to the works agreement
- [ ] Art. 30 record filled in from §2, DPO assessment on file
